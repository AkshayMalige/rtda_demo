Where this is going

Thirteen steps, and they build in one direction: from a single machine instruction up to a 14-layer network you can rebuild yourself. Each step exists because the previous one ran into a wall. Here is the whole argument, so you always know which wall you are standing at.

How to read this if it starts feeling abstract

Three colours are used consistently in every diagram, and they always mean the same thing: input data, weights, results and accumulators. Grey is waste or padding.

And whenever a number appears — 4, 8, 128, 16 KB, 512 — it comes from one of three places: the size of a piece of silicon, a division you can do yourself, or a measurement this repo took. The last section lists the source of every one of them. Nothing here is a tuning constant somebody guessed.

STEP 1

The hardware can do exactly one thing

Forget neural networks for a minute. The AIE-ML vector unit has one instruction that matters to us. It multiplies a small block of numbers by another small block of numbers and adds the result into a wide accumulator.

input data weights result / accumulator wasted or padding

Three letters, and they never change meaning:

The one thing to hold onto

The hardware does not multiply a vector by a matrix. It multiplies a 4-row block by a matrix. Whether you have 4 rows of real data or not, it computes 4 rows.

Why 4×8×4? The answer is one number and it is not negotiable

Because the AIE-ML vector unit performs 128 bfloat16 MACs per cycle, and 4 × 8 × 4 = 128. The atom is one cycle's work, arranged so that each of its three operands is exactly one 512-bit register.

This is the first question everyone asks, and it has a genuinely satisfying answer. AMD's architecture manual states the vector unit's throughput directly: "Vector unit supports 256 (8b × 8b) and 512 (4b × 8b) MAC operations" and "Vector unit supports 128 bfloat16 MAC operations with FP32 accumulation."

You do not invent an mmul shape; you pick one the library implements for your data type. That list lives in a header on this machine — $XILINX_VITIS/aietools/include/aie_api/detail/mmul.hpp — and for AIE-ML it reads:

Read that table again — it is the whole design rule

For both of this project's precisions, 4×8×4 is the only shape the hardware issues in one go. The bigger bf16 entries — 8×8×4, 8×8×8 — are marked ᵃ: the library builds them out of several 4×8×4 instructions. They are a convenience, not a wider machine.

That is why gen_graph.py can say this and mean it:

# On AIE-ML both use the SAME aie::mmul microtile, (4,8,4) -- see
# op_impls/families/matmul/common.py MICROTILE_OPTIONS -- so BATCH stays 8
# and the whole batching argument is unchanged by the precision switch.

And the practical consequence is the useful part: because the atom does not change with precision, everything you learn in this tutorial stays true when you switch to bf16. Only the speed changes — and Step 2 is about why it changes so much.

Check yourself

The int8 row offers 4×8×8 natively, twice the outputs of our atom. Why does an int8 network get a bigger atom than a bf16 one?

Answer

Because the MAC budget is per cycle, not per shape, and int8 gets a bigger one: 256 int8 MACs/cycle against 128 for bf16. 4 × 8 × 8 = 256. Same arithmetic, different budget.

Which is the general rule: find your type's MACs/cycle, factor it into M·K·N, and the shapes on the menu will be the sensible factorisations of that number. If you ever want to know why a shape is missing, check whether it multiplies out to your type's per-cycle budget.

STEP 2

There is no float32 multiplier on this chip

AIE-ML deleted the fp32 vector datapath that AIE-1 had. Your aie::mmul<4,8,4,float,float> compiles — but into nine bfloat16 matrix multiplies plus the arithmetic to split and recombine them.

This is the single most important thing that is true of this design and is easy to miss, because nothing warns you. The fp32 build compiles cleanly, runs, and matches the ONNX reference to 7.5e-07. It just costs about nine times what you think it costs.

AMD's architecture manual is blunt about it:

AM020, AIE-ML Processor

"32-bit floating-point vector data path is not directly supported but can be emulated via decomposition into multiple multiplications of 16 × 16-bit."

And the AI Engine API header says the same in a footnote to the shape table: "float multiplications are emulated on AIE-ML/XDNA 1 using native bfloat16 multiplications."

What "emulated" actually costs — from the source on your disk

The emulation is not hidden. It is C in $XILINX_VITIS/aietools/data/aie_ml/lib/me_vmult_float_emulated.h. Each fp32 operand is split into three bf16 terms — a coarse term, a correction, and a correction to the correction — and then every cross product is accumulated:

// mac_4x8_8x4_accuracy_safe_inner(), the DEFAULT. A splits into a,b,c; B into d,e,f.
v16accfloat tmp = mul_4x8_8x4_conf(c, f, sub_mul);
tmp += mul_4x8_8x4_conf(c, e, sub_mul);
tmp += mul_4x8_8x4_conf(b, f, sub_mul);
tmp += mul_4x8_8x4_conf(a, f, sub_mul);
tmp += mul_4x8_8x4_conf(b, e, sub_mul);
tmp += mul_4x8_8x4_conf(c, d, sub_mul);
tmp += mul_4x8_8x4_conf(b, d, sub_mul);
tmp += mul_4x8_8x4_conf(a, e, sub_mul);
tmp += mul_4x8_8x4_conf(a, d, sub_mul);   // nine of them
Why this reframes the whole fp32-vs-bf16 comparison

The natural story — "bf16 is half the bytes, so it's a bit faster" — is wrong here, and being wrong about it leads you to the wrong optimisation. The truth is sharper:

  • bf16 is the machine's native type. One mac, one cycle.
  • fp32 is a software construction on top of it. Nine macs, plus the split, plus double the operand bytes to load (32 floats = 1024 bits = two register loads per operand rather than one).

So the honest framing of this project's two builds is not "the same design at two precisions". It is "the design, and the design run through a 9× emulation layer" — which is a completely reasonable thing to do when you want 7.5e-07 against the reference, and a completely unreasonable thing to do by accident.

Check yourself

If fp32 costs 9× the mmuls, why is the measured II ratio only 4.03× (4161 vs 1033 ns)?

Answer

Because the bf16 build is no longer limited by the vector unit. This repo's own performance scan measured 39.4% of the bf16 design's time outside the array, against 3.4% for fp32 — and that fraction does not fall as you go from 1000 to 10,000 events, so it is not launch overhead. The suspect is the output DMA: the 27 outputs come back as fp32 in both precisions, so bf16 halves the input and changes the output not at all.

Read the numbers this way: fp32 at 4161 ns is telling you about the emulation. bf16 at 1033 ns is telling you about the DMA. They are measuring two different bottlenecks, which is exactly why the ratio is neither 9 nor 2.

If you take one action from this document

Before optimising anything else in an fp32 AIE-ML design, try -DAIE_FP32_EMULATION_ACCURACY_FAST and measure both the II and the error against your reference. You are trading 9 mmuls for 6. This project has a trusted reference and a one-command crosscheck, so the experiment costs a build — and if the error stays inside 1e-4, it is close to free throughput.

The reason to be careful rather than eager: the modes differ in how many correction terms survive, so the ones you drop are exactly the low-order bits that the 7.5e-07 figure is made of. Measure, do not assume.

STEP 3

Why your first design was slow

The archived GEMV design fed the network one track at a time. One track is one row. So M was effectively 1.

But the instruction still computes 4 rows. The other three get fed nothing useful, and their answers are thrown away.

Why no compiler flag fixes this

The instinct on seeing "25% utilisation" is to look for a switch. There isn't one, and it is worth understanding why, because it tells you what kind of problem this is.

The compiler's job is to schedule the instructions you asked for. You asked for a matrix × vector. It compiled a matrix × vector — correctly, efficiently, using the only matrix instruction the chip has. The waste is in the shape of the request, not in the translation of it. No amount of optimising a 1-row multiply turns it into a 4-row multiply; only feeding it four rows does that, and only you know where to find four rows.

Which is the general lesson: on this device the compiler cannot restructure your dataflow. Matching the hardware's shape is your job, and it is nearly all of the job.

That single fact is the whole 29× speedup. Everything that follows is just the bookkeeping needed to fill those rows.

STEP 4

Fill the rows: process tracks in blocks

The fix is embarrassingly simple to state. Instead of pushing track 0 through the whole network, then track 1, then track 2 — push tracks 0,1,2,3 through together.

Nothing about the maths changes. Track 0's answer does not depend on track 1. They just ride the same instruction.

One output, computed by hand

Take the embedding layer's first weights and a real track from model/weights_fp32/. Compute one cell of C — track 0's output feature 0. Get a calculator out; this is checkable.

weight column 0           -0.339  -0.153  +0.062  -0.116  +0.081  +0.086

add them up                                                       = -0.1128

That is one cell of C, and the layer has 128 of them per track.

Now the important part: C[1][0] — track 1's output feature 0 — uses the very same weight column, just a different row of data. So does track 2, and track 3. The hardware loads that column once and uses it four times.

The weights get loaded once and used for all 4 tracks. That is the second win, and it is why the weight-load traffic, not the MAC count, is what batching really attacks.

Check yourself

The layer is 6 features wide, but K = 8. What happens to the other 2?

Answer

They are zero-padded. The weight matrix gets rows of zeros, so those lanes contribute nothing. The kernel never knows — the padding is done once, when the weights are prepared (gen_graph.py's load_weights builds a zeros((INPUT_DIM, HIDDEN)) and copies the real 6 rows into it). This is why parameters.h says IN_FEAT = 16 for a 6-feature input: padded up, and to 16 rather than 8 for a separate memory reason you meet in Step 10.

Why 8 tracks, not 4

Look at the real loop nest in dense_bias_relu.cpp. Both outer loops step by two, and four accumulators are live:

for (unsigned z = 0; z < rowA / M; z += 2) {        // over the BATCH, two blocks at a time
  for (unsigned j = 0; j < colB / N; j += 2) {      // over OUTPUT features, two at a time
    MMUL C00, C01, C10, C11;                       // FOUR independent accumulations
    ...
    for (unsigned i = 1; i < colA / K; ++i)         // over INPUT features — the reduction
      chess_prepare_for_pipelining
    {
      C00.mac(A0, B0);  C01.mac(A0, B1);
      C10.mac(A1, B0);  C11.mac(A1, B1);
    }
Why four accumulators, and why the batch is a multiple of 8

An mmul has latency: the result is not ready the cycle after you issue it. Keeping two row-blocks × two column-blocks = four independent accumulations in flight means the vector unit always has work that does not depend on an instruction still in the pipe. That is software pipelining, done by hand, and it is why the kernel reads the way it does.

The cost is that the batch must be a multiple of 2 × M = 8. The kernel asserts it:

static_assert(ConfigT::padded_independent_extent % (2 * ConfigT::M) == 0,
              "padded_independent_extent must be divisible by 2*M");

Ask for a batch of 4 and padded_independent_extent rounds it to 8 and does identical work — which is exactly why batch 4 and batch 8 were measured to take the same time. 8 tracks cost the same as 4. Note also the four accumulators are four 512-bit accumulator registers held live across the whole reduction; that is the real budget being spent here.

STEP 5

Real layers are bigger than the atom. Tile them.

A layer is a big rectangle. The atom is a small rectangle. Cover one with copies of the other — but the two directions you can move in mean different things, and that difference decides the whole design.

Our atom handles 4 tracks × 8 features → 4 outputs. A real layer is 128 features → 128 outputs. Let's be exact about how far apart those are.

questionarithmeticanswer
How many atoms across? (outputs)128 outputs ÷ N=432
How many atoms down? (inputs)128 features ÷ K=816
Atoms for 4 tracks32 × 16512
Multiply-accumulates in those512 × (4×8×4)65,536
Sanity check: 4 tracks × 128 × 128the same number65,536

The last two rows agreeing is the point of the table. Tiling does not add work. It is the same multiplies, in a different order — an order the hardware can actually execute.

STOP. Atoms are time; tiles are space.

This is the single most important distinction in the document, and if the rest has felt like it doesn't add up, this is almost certainly why.

512 atoms does not mean 512 tiles. It means 512 executions of one instruction — a loop. One tile can run all 512, one after another, in about half a microsecond. A tile is a small processor; running a loop is what it does.

  • Atoms are TIME. How many times the instruction issues. Decided by the layer's shape ÷ the atom's shape.
  • Tiles are SPACE. How many processors hold a piece of the problem. Decided by one thing only — whether a tile's weight slice fits in the bank it was given.

They are almost independent. Splitting a layer over 8 tiles does not change how many atoms there are; it changes who runs which ones, and they run at the same time instead of one after another.

Why this distinction is the whole design

Everything in Step 6 falls out of it. Ask what happens if you put two atoms on two different tiles:

  • Two atoms from across (different outputs) — the tiles never need to talk. Split them anywhere, on any two tiles, in any order. Free.
  • Two atoms from down (same output, different input slice) — one tile holds half an answer and the other holds the rest. Somebody has to add them, which means a wire between the tiles and a rule about who goes first.

So "how do I split a layer that doesn't fit" has two very different answers with two different costs, and picking between them is the actual engineering.

STEP 6

Splitting a layer: chains and cascades

The 256→128 solver layer holds 256 × 128 = 32,768 weights, at 4 bytes each in float32 = 128 KB. It needs 8 tiles. But which eight, and split which way? You already know there are two directions. Now they get their names.

The cascade, and why it costs no precision

Four people add up a long shopping list together. Each takes a quarter of the items. Person 1 totals theirs and passes the running total to person 2, who adds theirs on top. Person 4 has the answer.

The cascade is a dedicated hardware link between horizontally adjacent AIE-ML tiles that carries that running total. It is 512 bits wide — which is exactly MMUL::size_C = 16 accumulators × 32 bits — and it carries the raw accumulator, not a rounded output. In the code that is the whole difference between the four kernel roles:

// dense_first: compute a partial sum, hand it on unrounded
writeincr(outCascade, C00.to_accum());

// dense_middle / dense_last: RESUME someone else's accumulator, don't restart
MMUL C00(readincr_v<MMUL::size_C>(inCascade));
C00.mac(A0, B0);                       // keep accumulating on top

So a 256-input layer split across 4 tiles is bit-identical to the same layer on one tile. You split the work without splitting the precision. That is why the fp32 build reaches 7.5e-07 against ONNX rather than drifting a little at every hop.

Two details worth knowing about the cascade

It has a small FIFO. AM020 describes "a small, two-deep, 512-bit wide FIFO on both the input and output streams that allow storing up to four values between AIE-MLs". So a cascade stage can run slightly ahead of its neighbour without stalling instantly — but only by four accumulator words. Beyond that the producer blocks.

It constrains placement, hard. Cascade partners must be physically adjacent. That is why place_graph() in dense_bias_relu_graph.h computes an explicit adf::tile(tileCol, tileRow) for every kernel rather than letting the mapper choose, and why parameters.h carries a col_placement / row_placement pair per layer. On this device, cascade depth is a floorplanning decision.

Why 2 chains and not 4? Work all three options

A 128→128 layer is 64 KB of weights, so it needs 4 tiles. There are exactly three ways to arrange 4 tiles, and it is worth checking all of them — because the winner is not the one the latency rule picks.

arrangementwhat each tile holdsbytes/tile (fp32)fits?cascade depthreader ports on the input memtile
1 × 4 — one chain, 4 deep32 inputs × 128 outputs16 KByes4 — worst1
2 × 2 — two chains, 2 deep64 inputs × 64 outputs16 KByes22
4 × 1 — four chains, no cascade128 inputs × 32 outputs16 KByes1 — best4 — too many

All three fit the memory exactly. So memory does not decide this one — it already did its job by saying "4 tiles". On latency alone, 4 × 1 should win: no cascade at all, nothing waiting for a neighbour. And it is chosen against anyway, for a reason that has nothing to do with either arithmetic.

The real limit: a memory tile has 6 outgoing DMA channels

Every chain has to be fed. Four independent chains means four separate read streams out of the shared buffer holding the layer's input — and an AIE-ML memory tile has six MM2S (memory-to-stream) channels and six S2MM, total, shared with everything else reading that buffer. It also has only 48 buffer descriptors across all twelve channels. Ask for 4 chains on the 128-wide layers and you run out.

gen_graph.py says so in as many words:

# cas_num is capped at 2 on the 128-wide layers: the default of 4
# saturates the 6 MM2S DMA channels of a memory tile.

So 2 × 2 is the compromise: the best cascade depth still reachable within the channel budget. The rule picked 4 × 1; a countable resource elsewhere overruled it.

That pattern — a clean principle, overruled by some other resource you have to go and count — is most of what designing for this device feels like. It is also why "why is it 2?" almost never has an answer in the layer's own arithmetic.

Check yourself

The 256→128 layer uses 2 × 4 = 8 tiles, so its cascade is 4 deep — the depth we just called "worst". Why is that acceptable there?

Answer

Because it has no choice. 256 × 128 × 4 B = 128 KB needs 8 tiles, and chains are capped at 2 by the same DMA limit — so 8 ÷ 2 = a cascade 4 deep. The options were 2 × 4 or nothing.

Note what that means for the whole design: the deepest cascade in the network is set by the widest layer, and the widest layer exists because the roll-concat doubles 128 features into 256. The cost of that concatenation shows up here, four tiles away from where it was introduced.

One deliberate non-optimisation

The cascade lengths in this project are pinned by hand, not chosen by the tool. bf16 halves the weight bytes, so the resolver would happily give it shorter cascades than fp32 (emb_d1 2→1, solver d0 4→2) — and then the two builds would differ in parallelism as well as precision, and no comparison between them would mean anything. Pinning keeps precision the only variable.

The price is visible in the build: in bf16 each tile's 64×64 slice is only 8 KB, so half of the weight bank sits empty. That is the cost of a controlled experiment, paid knowingly.

STEP 7

Where everything actually lives: banks, neighbours, ping-pong

A tile has 64 KB in four banks of 16 KB. This design gives the weights a whole bank of their own, puts the output ping-pong in two more, the stack in the last — and then borrows the neighbouring tile's memory for the input.

The 64 KB, precisely

AM020 states it exactly, and the "programmer's perspective" sentence is the one that matters:

AM020, AIE-ML Tile Architecture

"Data memory is increased from 32 KB to 64 KB organized as eight banks of 8 KB from a hardware perspective. From a programmer's perspective, every two banks are interleaved to form one bank, that is, a total of four banks of 16 KB."

So "16 KB" is not folklore. It is the granularity you actually allocate in, and the kernel enforces it as a compile error:

static_assert(OUT_FEAT_SLICE * IN_FEAT_SLICE * sizeof(weight_t) <= 16384,
              "Weight size per tile must not exceed one AIE-ML memory bank (16 KiB)");

The bank map this design actually gets

Here is where the tutorial you may have read before was wrong, and where the truth is more interesting. The placement is written out explicitly in dense_bias_relu_graph.h:

    adf::bank(tileCol - 1, tileRow, 3)                  // ...and its bank 3          (pong)
};

  adf::location<adf::buffer>(kk[idx].out[0]) = {        // the OUTPUT block...
      adf::bank(tileCol, tileRow, 0),                   // ...own bank 0 (ping)
      adf::bank(tileCol, tileRow, 3)                    // ...own bank 3 (pong)
  };
  ... bias -> adf::bank(tileCol, tileRow, 1);
}
Why one array per bank, when the hardware would let you span banks

Nothing in the silicon forbids a 32 KB buffer spanning two banks. The reason this design pins one array per bank is bank conflicts. In the inner loop the vector unit issues, every iteration, a load of A and a load of B and eventually a store of C. If two of those live in the same bank, the accesses serialise and the pipeline stalls — and the loop you carefully filled with four accumulators is suddenly waiting on memory.

So the discipline is: give each thing the unit touches simultaneously its own bank. Which is why weights get bank 2 alone, why input ping and pong are banks 0 and 3 (not 0 and 1), and why the input had to move next door at all — there simply were not four free banks on one tile.

Take this as the general rule, not a quirk: when you write your own design, the bank budget is not "64 KB, spend it how you like". It is "four slots, and things that are read in the same cycle must not share one".

Ping-pong, in three different mechanisms

"Double buffering" shows up three times in this design under three different names. They are worth separating, because they are configured in different places:

The trap hiding in that table

single_buffer() on the weight port is not a micro-optimisation — it is load-bearing. Without it the port is double-buffered and a 16 KB weight slice needs 32 KB, which is two banks, which breaks the whole allocation scheme. If you copy this design's structure and forget that one line, your static_assert still passes and the mapper fails later with an allocation error that says nothing about weights.

The same reasoning says why it is safe: a double buffer exists so a writer and a reader can proceed at once. The weights have no concurrent writer after startup. There is nothing to overlap.

Check yourself

65 dense tiles out of 304 on the device. Why not use all 304 and go ~4× faster again?

Answer

Because there is nothing left to split. Splitting is driven by the weight-bank limit, and every layer but the first already sits exactly at 16 KB per tile — you cannot divide a layer further without tiles that hold less than they could, and the chain count is already capped by the memtile's 6 read channels.

You could run more copies of the whole network side by side on the spare tiles and process several independent track streams at once. That is a throughput win, not a latency win, and this design did not need it: the fp32 build spends only 3.4% of its time outside the array. There is no headroom to reclaim by adding tiles, because the array is not what you are waiting for.

STEP 8

Weights: the right order, and how they get there

Two separate questions, usually confused. What order are the numbers in? and what pushes them onto the tile? Take them one at a time.

Part A — the order

The numbers are the same. Only their order in memory changes — and it changes to match the order the kernel will ask for them in.

The kernel grabs weights 32 at a time — one whole 8×4 block, in one memory read:

aie::vector<weight_t, MMUL::size_B> B0 = aie::load_v<MMUL::size_B>(pB1);
pB1 += MMUL::size_B * (colB / N);      // then jump to the next K-slice

For that to be a single fast load, those 32 numbers must be next to each other in memory. But in a normal row-major weight matrix, an 8×4 block is scattered across 8 different rows.

Why not just let the hardware gather them?

Because a "gather" is not one operation. Reading 32 contiguous numbers is a single instruction. Reading 4 numbers from each of 8 different rows is eight separate reads plus the address arithmetic to work out where each row starts — and it happens inside the innermost loop, the one that runs hundreds of times per layer per block of tracks.

So you have a choice about where to pay the cost of the mismatch: once, on the host, before the run starts — or several times per atom, forever. The rearrangement is the same work either way. Doing it once is free; doing it in the loop is the design.

This is the same trade as the bias in Step 9 and the reshape in Step 10, and it is worth naming: move work out of the inner loop and into setup wherever the shape lets you.

The packer is in analysis/rtda_reference.ipynb §1 and it is the clearest statement of the layout:

def pack_mmul(Wm, K, N, K_slice, N_slice, mk, mn, cas_length, cas_num):
    tk, tn = K_slice // mk, N_slice // mn          # micro-tiles per slice
    out = np.zeros((cas_num, cas_length, tk * tn * mk * mn), np.float32)
    for c in range(cas_num):                       # which output CHAIN
        n_base = c * N_slice
        for s in range(cas_length):                # which CASCADE STAGE
            i = 0
            for kt in range(tk):                   # walk K in steps of mk = 8
                gk = s * K_slice + kt * mk
                for nt in range(tn):               # walk N in steps of mn = 4
                    tile = Wm[gk:gk+mk, gn:gn+mn]  # an 8x4 block
                    out[c, s, i*mk*mn:(i+1)*mk*mn] = tile.ravel('C')
                    i += 1
    return out

Read that as: for each (chain, cascade stage), emit the 8×4 blocks of the weight matrix in K-major, N-minor order, each block flattened row-major. Note that the split across tiles and the micro-tile packing happen in the same function — because they are the same act of slicing.

Why this matters more than it looks

If you pack the weights wrongly, the graph still runs, still produces plausible-looking numbers, and is wrong. There is no crash to tell you.

That is why this project checks it: the notebook re-packs the weights from model/weights_fp32/ and compares against all 92 payloads actually loaded onto the card, expecting 0.000e+00. Do this for any model you map. It is twenty lines and it has caught real bugs.

Part B — RTP: the mechanism that gets them there

Weights arrive over RTP ports — run-time parameters. They are pushed once, before the run starts, and then sit on the tile forever, so every iteration is pure compute. Three lines in dense_bias_relu_graph.h set the whole policy:

connect<parameter>(wts[idx], async(kk[idx].in[1]));   // an RTP port, asynchronous
single_buffer(kk[idx].in[1]);                        // one copy, not ping-pong
connect<parameter>(bias[row], async(kk[idx].in[3])); // bias, same treatment

A real trap this project hit, twice

The bf16 type mismatch. Generated weight headers store bf16 as raw uint16_t bit patterns, because C++ has no portable bfloat16 literal. The RTP port, however, is typed bfloat16. Passing the array directly gives:

ERROR: adf::graph::update parameter type uint16 is inconsistent with
       RTP port dut.dut.emb_d0_aie.kk[0].in[1] type bfloat16

after which no weights arrive and the graph deadlocks — and the x86 simulator still exits 0 and prints "Simulation completed successfully". The fix is a reinterpret_cast (as_weights<Cfg>() in app.cpp), which is correct rather than lossy: the uint16 is the bf16 encoding.

The general lesson: an RTP that never arrives looks exactly like a graph that hangs for a scheduling reason. Verify the payloads landed (Part A's check) before you debug the dataflow.

STEP 9

Bias and ReLU cost nothing

In a straightforward design these are separate kernels — a bias-add tile, a leaky-ReLU tile, each with buffers and connections. Here they vanish, and it is worth seeing how, because the trick generalises.

Bias: start the tally at the bias

Normally you compute y = W·x, then add b. Instead, set the accumulator to b before you start multiplying. Then every multiply-accumulate lands on top of it:

auto bias_block_0 = replicate_rows<M, bias_t, N>(bias_v_0);  // same bias for all M tracks
C00 = bias_block_0;  C00.mac(A0, B0);                       // start the tally at b, not 0

Cost: zero extra instructions. A whole tile, buffer and hop disappear into the initial value of a register. replicate_rows is the only new idea — it copies the 4-wide bias vector across all M rows of the block, because every track gets the same bias.

For dense_last the bias is added after the cascade sum instead (C00 = aie::add(C00.to_accum(), bias_block_0)), since the accumulator arrives already loaded. Same idea, different insertion point — and note that this is why only the last tile of a chain has a bias port at all. That is where the 27, not 65, in the bias-port count comes from.

Leaky ReLU: fold it into the write

The result has to be converted from the wide accumulator down to float32 anyway before being stored. The activation is applied in that same moment, while the numbers are already in registers:

const auto y = acc.template to_vector<result_t>(SHIFT);      // the conversion you owed anyway
const auto slope = aie::broadcast<result_t, N>(result_t(ConfigT::LEAKY_ALPHA));
return aie::max(y, aie::mul(y, slope).template to_vector<result_t>());

About three extra vector instructions, total, per output block.

The general rule

Anything elementwise — bias, ReLU, scale, clamp, quantise — should be folded into the end of whatever produced the data. Never give it its own kernel.

A kernel costs you a tile, a buffer, a DMA transfer and a synchronisation point. An elementwise operation costs one instruction. The ratio is not close.

STEP 10

Moving data between layers, for free

Layer N writes its answers in one shape; layer N+1 wants them in another. On a CPU you would write a loop to shuffle them. Here you write a few numbers into a descriptor, and the shuffle happens inside a transfer that was going to occur anyway.

Here is the real problem. A dense layer writes its results in 4×4 blocks — that is size_C, 4 outputs × 4 tracks. The next layer wants to read them in 8×4 blocks — that is size_A, 8 features × 4 tracks. Same numbers, different grouping.

Why the regrouping is genuinely free, not just cheap

The data has to travel from the producing tile to the consuming tile regardless — they are different processors with different private memories. That journey is made by a DMA engine, and a DMA engine does not read straight through from start to finish. It walks the buffer following a buffer descriptor: so many elements, then skip so far, then so many more, up to four dimensions deep.

So the reshape rides along inside a movement that was already happening and already paid for. Nothing reads the data an extra time; nothing writes a second copy; no tile spends a cycle on it. You are choosing the itinerary of a trip, not adding a trip.

The descriptor, read as a sentence

From graph_plan.h, the buffer between the two embedding layers:

self.buffer_r_e0 = adf::shared_buffer<float>::create({128, 8}, 1, 2);  // 128×8, 1 writer, 2 readers
num_buffers(self.buffer_r_e0) = 2;                                    // double-buffered

write_access(self.buffer_r_e0.in[0]) = adf::tiling({
  .buffer_dimension = {128, 8},        // the memtile array: 128 features × 8 tracks
  .tiling_dimension = {4, 4},          // the producer delivers size_C chunks
  .offset           = {0, 0},
  .tile_traversal   = { {.dimension=0, .stride=4, .wrap=32},    // 32 steps of 4 along features
                        {.dimension=1, .stride=4, .wrap=2} }}); //  2 steps of 4 along tracks

  .buffer_dimension = {128, 8},
  .tiling_dimension = {8, 4},          // the consumer wants size_A chunks  <-- DIFFERENT
  .offset           = {0, 0}, ... });

read_access(self.buffer_r_e0.out[1]) = adf::tiling({
  ...
  .offset           = {64, 0}, ... }); // the SECOND reader starts at feature 64
Where the "multiple of 16" rule comes from

The memory tile has 48 buffer descriptors shared across its twelve DMA channels, with 24 reachable by any one channel. A tiling pattern that needs a fresh descriptor per row burns through them fast. gen_graph.py records what happened when the input was left at its natural width:

# At width 6 or 8 the input is padded 6->16, and that strided staging needs one
# memory-tile buffer descriptor per batch row, which exhausts the BD pool for
# batch > 8 ("[aiecompiler 77-4352] Failed to allocate buffer descriptors for
# buffer_x"). At width 16 the copy is contiguous and the problem disappears.

So INPUT_DIM = 16 for a 6-feature input is not superstition and not alignment for its own sake — it converts a strided staging copy into a contiguous one, and a contiguous copy needs one descriptor instead of eight.

STEP 11

The two things that aren't dense layers

Almost everything is handled by the machinery above. Two things aren't, and they are the ones you would still write by hand. Both are in src_fp32/kernels/, both are about 40 lines, and both are about state.

The roll-concat — a static is a state machine

Each track must be paired with the track before it, turning an [8][128] block into the [8][256] the solver's first dense wants. Within a block that is just "the row above". Across blocks it needs memory:

alignas(32) static float carry[FEAT] = {};      // <-- the entire semantic content

for (int t = 0; t < TRACKS; ++t) {
    const float* cur  = pi + t * FEAT;
    const float* prev = (t == 0) ? carry : (pi + (t - 1) * FEAT);
    // write [cur | prev] into a 2*FEAT-wide row
}
// hand this block's last track to the next invocation
Statics live from ELF load, not from graph.run()

Two consequences bit this project hard, and both are yours to own the moment you write a static:

  • The roll is streaming, not circular. The ONNX reference rolls circularly within a 50-track event — track 0 pairs with track 49. A streaming graph cannot do that without buffering the whole event, so the very first block's track 0 pairs with the zero-initialised carry, and every later block's track 0 pairs with the previous block's last track. That single difference is the origin of every "why don't my numbers match the reference" confusion in this repo, and it is why the comparison excludes a 3-track warm-up.
  • A second run starts warm. Running the graph again without reloading the ELF begins with the previous run's leftover carry. Fixed by pushing one all-zero flush event through first and discarding its result.

Rule: if your kernel has a static, you have a state machine, and you now own its reset semantics. Write them down before you build.

The averager — a rate mismatch you must express, not avoid

track_accum sums 50 tracks and emits one 128-wide result. But the graph requires every kernel wired to an output to write something on every single iteration. It cannot say "nothing this time." So it writes zeros six times out of seven, and the real mean on the seventh.

Why the graph insists, and where the 7 comes from

The whole array runs on a static schedule. Buffers, DMA descriptors and synchronisation are laid out at compile time on the promise that every kernel consumes and produces a fixed number of items per iteration. That promise is what makes the schedule computable, and what lets the design run with no runtime arbitration at all. A kernel that sometimes emitted nothing would break the arithmetic the scheduler was built from.

The 7 is the event size divided by the batch: 50 tracks per event, padded to 56 slots, at 8 tracks per iteration = 7 iterations — N_ITER in parameters.h. One event mean emerges every 7th iteration; the other 6 say zero.

And emitting zeros rather than a partial sum is a deliberate interface choice: the consumer does not need to know that 7 is the magic number. It can sum all frames, or take the non-zero one, and it stays correct if N_ITER changes.

The padding slots are not harmless — read this before you copy the pattern

An obvious implementation would sum all 56 slots and divide by 50. That is wrong here, and the kernel's own header explains why: every dense layer has a bias, so a zero input track still produces a sizeable output — measured |max| 0.13 against 0.49 for a real track. Summing 56 and dividing by 50 shifts every element of the mean by ~6.6% of signal.

So the kernel counts and stops at 50. Which introduces its own limitation, also written down: it counts slots consumed, not real tracks — it cannot tell them apart, because by the time a zero-input slot reaches here it carries a bias-determined activation like any other. Every event must therefore carry exactly 50 real tracks. A short final event yields a wrong mean (measured 8.0e-02 for a 20-track event) that still looks plausible.

This is what "expressing a duty cycle in a static-rate system" actually costs. Not a hack — a contract, with a precondition you must enforce upstream.

And one thing deliberately not on the AIE

The final 128→27 dense runs on the host CPU. It operates on a single averaged vector — one row. That is M=1, the exact shape this whole design exists to avoid. It is only 3,456 multiplies, 0.03% of an event, but it was measured at 15–19 µs on the array against 4.2 µs for the entire 14-layer pipeline. On the host it is free.

Knowing when not to use the accelerator is part of the skill. A batch-1 operation on a machine whose atom is four rows wide is a bad fit no matter how small it is.

STEP 12

The code, file by file

Everything above has a home. But before the map, the one fact that explains the shape of this tree:

Most of what you are about to read is generated

aie_batch/gen_graph.py builds the network as ONNX from the weights in model/weights_fp32/, hands it to a library called aie4ml, and aie4ml lowers each Gemm to an aie::mmul kernel and emits a normal Vitis AIE project: app.cpp, aie.cfg, and the whole of src_fp32/ or src_bf16/.

That matters for two reasons. First, do not hand-edit the generated files and expect the edit to survive make regen. Second — and this is the useful part — everything the generator emits is something you could have written yourself, and Step 13 shows you what the hand-written version looks like. The generator is a convenience, not a dependency: the output is ordinary ADF C++ with no runtime attached.

The three hand-written pieces, added on top, are roll_concat_batch, track_accum, and the wiring in top_graph.h / graph_plan.h that connects them. Those are the parts that were not expressible as an ONNX Gemm.

STEP 13

Building your own, by hand

Someone hands you a network. Here is the order of operations. Do the arithmetic before you write any code — the first four steps decide most of the design, and they are all division.

Phase 1 — arithmetic, no code

  1. Build a trusted reference first. A numpy or ONNX model you believe, and a fixed stimulus. Without it you cannot tell a mapping bug from a precision effect, and you will lose days to that confusion. In this repo that is model/rtda_ref.py + model/mlp_fp32.onnx, and every implementation is scored against it on the same data.
  2. Pick your data type, then look up its atom. Find MACs/cycle for that type (bf16: 128, int8: 256), factor into M·K·N, and confirm the shape exists in aie_api/detail/mmul.hpp. If you chose fp32, go back and read Step 2 first — you are choosing a 9× emulation.
  3. Weight bytes ÷ 16 KB = minimum tiles, per layer: 
    tiles ≥ ceil(IN_FEAT × OUT_FEAT × sizeof(weight_t) / 16384)
    This is the number that decides your design. Do it for every layer, in a spreadsheet, before anything else.
  4. Factor that tile count into CAS_NUM × CAS_LENGTH. Prefer more independent chains (shorter cascades, less latency) — then check the chain count against the feeding memtile's 6 MM2S channels, counting every other reader of that buffer too. That check is what will actually decide it.
  5. Batch = a multiple of 2·M (8 for our atom). Below that you are padding and paying anyway.
  6. Make every tensor dimension a multiple of 16 elements. Pad in the weight packer, never in the kernel. This is a buffer-descriptor constraint, not an aesthetic one.

Phase 2 — the four files you actually write

Stripped of generation, a layer is this much code. Write these four and you have a working dense layer on real tiles.

// same body with the accumulator's source and sink swapped:
//    single : bias -> accumulate -> activate -> ofm

//    middle : cascade in -> accumulate ->       cascade out
//    last   : cascade in -> accumulate -> bias -> activate -> ofm

      C00.mac(A0, B0); /* ...and the other three */
    }
    /* drain: store_v(apply_activation(Cxx)) or writeincr(cascade, Cxx.to_accum()) */

Checks 1 and 4 test the structure. Check 2 tests the arithmetic as simulated. Only check 3 tests that the bytes on the actual device are the bytes you meant — and a packing bug is the one class of error here that produces no crash, no warning, and output in the right range.

It is also the check people skip, because by the time you reach hardware you have already seen the design "work" three times.

The habits that outlast the API

  • Compute the tile count and the buffer bytes before writing code. If the arithmetic does not work, no amount of code will fix it.
  • Keep one trusted reference and score everything against it — always the same metric, always the same stimulus.
  • Distinguish a convention difference from an error. In this repo the 1.556e-02 is the circular-vs-streaming roll and the 7.5e-07 is arithmetic. Conflating them sends you hunting a bug that does not exist.
  • Measure II, not wall-clock. II is the array's true throughput; wall-clock includes host and DMA costs that do not scale with the array. This project's fp32→bf16 is 4.03× in II but 2.52× on silicon — and the difference is the finding, not noise.
  • When a number surprises you, measure the decomposition rather than reasoning about it. In the sister PL design in this repo, four changes were made to improve accuracy — and measuring them one at a time showed that three of the four were individually harmful. Nobody would have guessed that. Only the ablation showed it.

  2. Work out what L3Cfg's 8 tiles hold, weight slice by weight slice, and check your answer against pack_mmul.
  3. Change BATCH to 16 and make regen. Predict the tile count and the II before you measure.
  4. Build the fp32 design with -DAIE_FP32_EMULATION_ACCURACY_FAST. Predict the II (Step 2 gives you the ratio) and the error, then measure both.
